# Ravenfield prototype

Прототип многопользовательского шутера на Go, raylib-go и Jolt Physics. Текущее состояние — завершённый технический Этап 0 из [`SPECIFICATION.md`](SPECIFICATION.md) и начало Этапа 1, а не игровой MVP. Устройство сети, ботов и техники описано в [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Что работает

- 3D-клиент на raylib-go с тестовой сценой и капсульным контроллером;
- сервер запущен всегда: одиночная игра идёт через встроенный сервер, к которому клиент подключается через память;
- сетевая игра по QUIC: выделенный сервер или клиент-хост; клиент предсказывает своего солдата и плавно показывает чужих;
- болванки для нагрузки: сотни серверных солдат без ИИ (`-dummies`), профиль тика по системам в журнале сервера;
- снимки в бюджете трафика: дельты от подтверждённого состояния каждого солдата, компактная запись ботов, приоритеты с конусом взгляда — 256 болванок укладываются в 32 КБ/с на клиента;
- физика Jolt 5.7.0 через собственный CGo/C++-адаптер;
- динамические тела, лучи и отладочная отрисовка;
- скелетные анимации Idle, Walking и Running;
- регдолл из 13 тел с переходом из текущей позы и обратным переносом на модель;
- единый тик симуляции 60 Гц на клиенте и сервере (`game.TickRate`);
- модель «игрок / солдат / бот» и квантованная команда ввода `game.InputCommand`;
- слои столкновений с масками для лучей, пакетные лучи на общем пуле потоков Jolt;
- сохранение и восстановление состояния персонажа: повтор команд с любого тика совпадает побитово;
- бинарный протокол: подключение, команды ввода и снимки мира со строгим разбором и fuzz-тестом;
- транспорт через QUIC и через память с имитатором сети (задержка, джиттер, потери, дублирование);
- консольный сервер без raylib;
- QUIC-прототип с надёжными потоками и ненадёжными датаграммами.

## Требования

Проверенная конфигурация: Linux x86-64, Go 1.27.1, GCC 16.2, CMake 4.4, Ninja.

Для сборки нужны:

- Go с поддержкой CGo;
- C++17-компилятор;
- CMake и Ninja;
- Git для загрузки Jolt через CMake FetchContent;
- системные библиотеки, необходимые raylib (OpenGL, X11/Wayland и аудио для клиента).

Windows подготовлена как целевая платформа архитектуры, но сборка и запуск на ней ещё не проверены.

## Сборка

Из корня репозитория:

```sh
make native
make all
```

Или полностью через цели Makefile:

```sh
make client
make server
go build -o bin/netprobe ./cmd/netprobe
```

После сборки нативной библиотеки все Go-пакеты можно проверить командой:

```sh
go build ./...
```

`make clean` удаляет собранные бинарные файлы и нативный build-каталог. При следующей сборке Jolt будет загружен заново.

## Запуск

Клиент:

```sh
./bin/client
```

Управление:

- `WASD` — движение;
- мышь — обзор;
- `Space` — прыжок;
- `Shift` — спринт;
- `K` — перейти из текущей анимации в косметический регдолл (смерть решает сервер с Этапа 2);
- `R` — вернуть солдата на точку появления через сервер, убрать регдолл и сбросить шары;
- `F1` — отладочная отрисовка физики и серверное положение своего солдата рядом с предсказанным;
- `F3` — вид от первого или третьего лица;
- `Esc` — захват или освобождение курсора.

Автоматическая проверка одного цикла:

```sh
./bin/client -demo -frames=600
```

Три цикла создания и удаления регдолла:

```sh
./bin/client -demo -cycles=3 -frames=2600
```

Солдат теперь добегает почти до колонны и падает на неё; регдолл успокаивается дольше, чем на открытом полу, поэтому кадров больше.

Автоматический маршрут с разгоном, рампой и прыжком:

```sh
./bin/client -movement -frames=400
```

Маршрут должен закончиться на верхней платформе: ступни на `Y=1.50`, `grounded=true`. Движение считает встроенный сервер; итоговая точка совпадает с той, что давал клиент до появления сервера.

Тот же маршрут через имитатор сети (задержка в каждую сторону, джиттер, потери):

```sh
./bin/client -movement -frames=400 -netsim=delay=40ms,jitter=10ms,loss=2%
```

Потерянные датаграммы перекрываются повтором последних команд, поэтому маршрут заканчивается в той же точке. Клиент предсказывает своего солдата, так что управление не запаздывает; строка `corrections` в журнале и на экране считает случаи, когда сервер с предсказанием не согласился.

Дополнительные параметры `-debug`, `-width`, `-height`, `-frames`, `-screenshot`, `-tuning`, `-name` и `-netsim` показаны в `cmd/client/main.go`.

Шары тестовой сцены — косметика клиента: сервер пока не передаёт динамические предметы, и солдат их не толкает.

Параметры движения по умолчанию заданы в `game.DefaultMovementTuning`. Файл `-tuning` в формате JSON переопределяет только указанные в нём значения, например:

```json
{"walk_speed": 5, "sprint_speed": 8, "jump_speed": 6, "eye_height": 1.55}
```

Неизвестное поле или недопустимое значение останавливает запуск с ошибкой.

Автоматические тесты:

```sh
go test ./...
```

Fuzz-тест разбора сетевых сообщений:

```sh
go test -run='^$' -fuzz=FuzzDecode -fuzztime=60s ./internal/network/protocol
```

Сетевая игра на выделенном сервере (без графического окружения):

```sh
env -u DISPLAY ./bin/server -listen :7777
```

При первом запуске сервер создаёт `server.crt` и `server.key` и печатает отпечаток сертификата. Клиенты подключаются с этим отпечатком, чтобы попасть именно на этот сервер:

```sh
./bin/client -connect 127.0.0.1:7777 -fingerprint <отпечаток> -name Alice
```

Без `-fingerprint` клиент примет любой сервер и напечатает его отпечаток. Клиент может и сам стать сервером для друзей — он печатает отпечаток так же:

```sh
./bin/client -host :7777
```

Нагрузка из 256 болванок — солдат без ИИ, которые бродят по карте:

```sh
env -u DISPLAY ./bin/server -listen :7777 -dummies=256 -stats=2s
./bin/client -dummies=256
```

Журнал сервера показывает реальную частоту тиков, среднее и максимальное время тика, долю каждой системы и трафик снимков на игрока. Клиент рисует 16 ближайших солдат анимированными моделями, остальных — капсулами цвета команды; в верхней строке — трафик снимков за последнюю секунду.

Бюджет снимков на клиента задаёт `-client-bandwidth` в КБ/с (по умолчанию 32, вместе с оценкой заголовков UDP и QUIC). Сервер шлёт каждому клиенту сначала его солдата, людей и тех, кто у перекрестия, затем остальных по приоритету. Посмотреть, как делится урезанный бюджет:

```sh
env -u DISPLAY ./bin/server -listen :7777 -dummies=256 -client-bandwidth=8 -seed=1 -stats=2s
```

`-seed` фиксирует зерно матча, от которого зависит расстановка болванок, чтобы прогоны повторялись.

Без параметра `-duration` сервер работает до `SIGINT` или `SIGTERM`. Параметры `-max-players`, `-snapshot-rate`, `-cert`, `-key` и `-tuning` описаны в `cmd/server/main.go`; у сервера и клиентов должны быть одинаковые параметры движения.

QUIC-прототип:

```sh
./bin/netprobe -delay=40ms -drop-every=4
```

Параметр `-drop-every=4` отбрасывает каждый четвёртый UDP-пакет в обоих направлениях. Успешный запуск подтверждает восстановление надёжного потока и доставку датаграммы.

## Основные каталоги

- `cmd/client`, `cmd/server`, `cmd/netprobe` — исполняемые программы;
- `internal/physics` — Go API физики и владение ресурсами;
- `native/jolt` — C ABI и C++-адаптер Jolt;
- `internal/animation` — скелетные анимации и регдолл;
- `internal/game` — общая симуляция: солдаты, команды, движение, параметры;
- `internal/simulation` — авторитетный сервер: сессии, очередь команд, снимки;
- `internal/client` — клиент: встроенный сервер, сессия, отрисовка;
- `internal/network/protocol` — бинарный протокол сообщений;
- `internal/network/transport` — QUIC, память и имитатор сети;
- `internal/network` — QUIC-прототип Этапа 0;
- `assets/prototype` — временная CC0-модель и её лицензия.
